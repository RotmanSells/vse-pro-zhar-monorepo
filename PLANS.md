# Execution Plans

## Назначение

`PLANS.md` задаёт единый формат execution plans для coding agents. План описывает одну конкретную текущую задачу, а не весь продукт и не весь milestone.

Уровни планирования:

```text
Roadmap
   ↓
Milestone
   ↓
Execution Plan / Active Task
   ↓
реализация и verification
   ↓
Completed Task
```

`Roadmap` задаёт high-level направление, `Milestone README` описывает целый этап, а `Execution Plan` содержит конкретный результат, который должен получить агент сейчас.

## Где хранятся планы

- [Active plans](docs/exec-plans/active/) — текущие задачи в работе.
- [Completed plans](docs/exec-plans/completed/) — исторические карточки завершённых задач.
- [Milestones](docs/milestones/) — описание больших этапов.

Обычно в `active/` находится ноль или одна основная задача. Следующая подробная задача создаётся только после завершения и анализа предыдущей. Не нужно заранее писать подробные планы для всех будущих milestone.

## Lifecycle

1. Агент читает `AGENTS.md`, `README.md`, относящиеся документы `docs/` и текущий plan.
2. Перед реализацией фиксируются цель, текущее состояние, scope, ограничения и проверки.
3. Во время работы агент обновляет `Progress`, добавляет только реальные `Discoveries` и локальные записи в `Decision Log`.
4. Перед завершением агент выполняет acceptance criteria и все применимые команды из `Verification`.
5. После завершения plan переносится из `active/` в `completed/`, а `Outcome` заполняется фактическим результатом.

Агент не переходит самостоятельно к следующей Active Task. Новый execution plan принимается отдельно.

## Database policy

В проекте используется одна основная PostgreSQL database. Для текущего проекта canonical local database — `vse_pro_zhar_dev`. Локальные development-запуски, ручная browser-проверка, Backend и migrations должны использовать только настроенный `DATABASE_URL` этой database. Запрещено создавать или использовать `vse_pro_zhar_test`, другие `*_test` databases и отдельные локальные PostgreSQL databases. Исторические планы с прежними изолированными командами не являются инструкцией для нового запуска.

## Living document

Execution Plan — живой документ, а не только первоначальный prompt. Агент обязан обновлять его по мере реализации:

- в `Progress` отмечать выполненные пункты через `- [x]`;
- в `Discoveries` записывать неожиданные факты, которые влияют на работу;
- в `Decision Log` фиксировать только локальные технические решения в рамках разрешённого scope;
- в `Outcome` описывать то, что реально сделано, а не копировать первоначальный план.

Если решение меняет утверждённую архитектуру, ADR или public contract, его нельзя легализовать одной записью в plan. Нужно остановиться, следовать `AGENTS.md` и получить owner decision.

Не записывай банальности, неподтверждённые предположения или несуществующие результаты.

## Обязательный формат одной задачи

Каждая полноценная coding task должна использовать следующий шаблон:

```markdown
# Название задачи

Status: planned | in_progress | blocked | completed
Milestone: M0
Depends on: предыдущая задача или none

## Purpose

Зачем выполняется задача и какой конечный результат нужен.

## Current State

Какое проверенное состояние repository существует перед задачей.

## Scope

Что входит в задачу.

## Out of Scope

Что явно запрещено делать в рамках задачи.

## Architecture / Constraints

Какие существующие архитектурные границы и обязательные правила нужно соблюдать.

## Implementation Requirements

Конкретные технические требования и ожидаемые интерфейсы.

## Tests

Какие automated и manual tests обязательны.

## Acceptance Criteria

Однозначные критерии завершения.

## Verification

Точные команды и действия проверки.

## Progress

- [ ] Подготовить реализацию.
- [ ] Выполнить проверки.
- [ ] Обновить Outcome.

## Discoveries

Только важные факты, найденные во время реализации.

## Decision Log

Локальные технические решения и причины.

## Outcome

Фактический итог после завершения.
```

`Status`, `Milestone` и `Depends on` должны быть заполнены явно. Для небольшой задачи допускается компактный вариант, но смысл обязательных секций сохраняется.

## Definition of done для execution plan

Задача завершена только когда:

- acceptance criteria выполнены;
- применимые automated и manual checks прошли;
- `Progress` отражает фактическое состояние;
- важные discoveries и решения записаны честно;
- `Outcome` заполнен фактическим результатом;
- документация не противоречит repository;
- plan перемещён в `completed/`, если задача действительно завершена.
