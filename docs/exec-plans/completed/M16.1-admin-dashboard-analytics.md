## Analytics Definition Gate

Перед реализацией metrics зафиксировать в plan точные правила. Рекомендуемый conservative baseline:

### Timezone and periods

- Timezone: `Europe/Moscow`.
- Supported periods: 7, 30, 90 calendar days including current day.
- Comparison period: предыдущий период такой же длины.
- Date boundaries вычисляет Backend.
- Client передаёт только enum period, а не произвольный SQL/date range.
- При нулевом previous value comparison возвращается `null`/`not_available`, а не fake `+100%`.

### Revenue

- Revenue — сумма `order.totalMinor` только по orders, которые имеют подтверждённый succeeded payment и подтверждённый completed business outcome.
- Canceled, unpaid, pending и unknown orders не входят в revenue.
- Refund/cancellation policy должна быть отражена явно; refund не считается успешной выручкой без approved accounting policy.
- UI форматирует integer minor units в RUB, но не меняет значение.

### Orders

- KPI `Заказов` должен иметь явно записанный scope: рекомендуемый baseline — количество server-created orders в выбранном периоде с отдельным breakdown по status.
- Нельзя молча смешивать created, paid, completed и canceled counts.
- Chart `Статусы заказов` показывает bounded server aggregation по известным statuses.

### Average check

- Рекомендуемый baseline: revenue / count of qualifying revenue orders.
- При нуле qualifying orders значение `null`/`—`, не `0₽` как fake business fact.
- Деление выполняется безопасно и только после integer aggregate.

### Customers

- Рекомендуемый baseline: distinct Customer IDs, связанные с qualifying orders в выбранном периоде.
- Anonymous/unknown customer rows не должны создавать fake customer identities.
- Comparison считается Backend.

### Series and top lists

- Revenue series содержит одну точку на календарный день, включая дни с нулём qualifying revenue как explicit zero/empty per contract.
- Top dishes строится из immutable order item snapshots квалифицируемых orders.
- Popular categories строятся из authoritative product/category mapping at order time, либо возвращают unavailable при отсутствии безопасного snapshot.
- Recent orders ограничены server-side, сортируются по `createdAt DESC`, не содержат raw provider payload.
- Order type chart показывает только реальные поддерживаемые types; при текущем pickup-only product scope delivery не должна появляться как fake data.

Если owner меняет любую из этих definitions, изменение фиксируется в Decision Log до implementation.

## Scope

### Contracts

Добавить strict shared contracts для:

- Dashboard query input: bounded enum `7 | 30 | 90`;
- KPI values;
- comparison values;
- daily revenue series;
- top dishes;
- status/category/type distributions;
- recent order row;
- CSV export response/file metadata, если export включён в slice;
- loading/empty/unavailable/reconciliation-safe response states.

Contracts должны:

- reject floats where integer money is expected;
- reject negative counts;
- reject unknown fields;
- bound array lengths;
- reject invalid dates/timezones/statuses;
- never expose SQL/provider internals.

### Database/repositories

- Реализовать bounded analytics repository queries поверх существующей schema.
- Использовать server-side filtering/grouping, не выгружать все orders в Node для client-like aggregation.
- Добавить только измеренные индексы, если query plan подтвердит необходимость.
- Не добавлять отдельный analytics database или cache.
- Historical values должны использовать order/item snapshots.
- Query result должен быть deterministic для одинакового DB state/time boundary.
- Добавить migration только если для утверждённых query boundaries объективно нужна новая schema/index.

### Backend service/routes

- Protected `GET /admin/analytics?days=7|30|90` или owner-approved equivalent.
- Existing staff guard and origin rules.
- Safe error mapping for validation, unavailable, reconciliation and database failure.
- Request ID/logging without PII/secrets.
- No mutation and no provider call.
- Optional protected CSV export must use same server-owned query definitions and bounded output.

### API client/controller

- Runtime-validated Admin Analytics client.
- Request controller with loading, retry, abort and latest-request-wins behavior.
- Period change cancels/invalidates stale response.
- No analytics calculation in UI.
- No direct environment/DOM/database/provider access.

### Admin UI

- Enable Dashboard sidebar item only when screen is actually wired.
- Implement exact prototype page structure.
- Add loading state for all KPI/chart/table blocks.
- Add page-level error with retry.
- Add empty/no-data charts without fake bars.
- Add safe unavailable/reconciliation state.
- Format currency and dates consistently with current Admin conventions.
- Preserve current Admin auth/logout/navigation.
- Preserve Catalog, Orders, Loyalty, Wheel and Quests screens.

### Export

Prototype has `Экспорт CSV`. If included in M16.1:

- export is generated from Backend, not browser reconstruction;
- content is aggregate-only by default;
- period is validated server-side;
- filename/date range are server-controlled or validated;
- CSV injection is prevented;
- no unbounded PII export;
- export failure is visible and retryable.

If export policy is not approved, keep the button visually present but disabled with truthful unavailable explanation, or record export as a follow-up—not as a fake download.

## Decision Log

- M16.1 выделен в отдельный read-only analytics slice; Promos, Customers, Segments и Messages не входят в эту задачу.
- Prototype Dashboard design переносится точно, без redesign и без импорта prototype data.
- Revenue/average check/customer/order semantics должны быть зафиксированы до write-кода; client-side aggregation запрещена.
- Definition Gate: timezone `Europe/Moscow`; диапазоны `[currentDay - days + 1, nextCurrentDay)` и предыдущий `[currentDay - 2*days + 1, currentDay - days + 1)`; сравнение при нулевом baseline — `null`.
- Definition Gate: qualifying revenue order — `orders.status = completed`, `orders.currency = RUB`, matching `payments.status/provider_status = succeeded`, и отсутствие refund со статусом `pending`, `succeeded` или `reconciliation_required`; неизвестные/несогласованные источники исключаются из успешной аналитики.
- Definition Gate: `orders` KPI и status/type distributions используют все orders с известными status в выбранном периоде; customers и item/category aggregates используют только qualifying revenue orders.
- Authoritative sources: order totals/status/createdAt — `orders`; payment fact — `payments`; customer identity — `order_customer_snapshots` с fallback на `customers` только для safe display name; item popularity — `order_items` snapshots; categories — unavailable because historical category snapshot is absent.
- Analytics работают на canonical `vse_pro_zhar_dev` и обычных bounded PostgreSQL queries; новая инфраструктура не нужна.
- Push/SMS/email providers остаются вне M16.1.
- CSV включён в slice: Backend возвращает bounded aggregate-only файл, защищённый от CSV injection; recent orders/customer names в экспорт не включаются.
- Для pickup-only scope chart заголовок production UI назван `Способ получения`, а data содержит только фактический `pickup`.
- Completed order без matching succeeded payment либо с pending/succeeded/reconciliation refund помечается `reconciliation_required`; он не превращается в успешную revenue цифру.
