# M13.5 — Списание угольков и реальные rewards

Status: completed
Milestone: M13.5
Depends on: M13 Loyalty, M1 Catalog, M7 Orders, M8 Card Payment, M9–M10 iiko Fulfillment

## Purpose

Добавить безопасное использование накопленных угольков и выдачу настоящей награды клиенту.

После задачи Customer сможет:

- увидеть доступные награды и их стоимость в угольках;
- выбрать награду и подтвердить списание;
- получить только подтверждённую Backend-награду;
- увидеть историю списаний и статус выдачи.

Admin сможет управлять каталогом наград, но не сможет вручную менять баланс, XP, rank или ledger.

## Current State

- `loyalty_accounts` хранит integer XP и `coalBalance`.
- `loyalty_ledger` уже поддерживает `entryType=spent`, `sourceType=redemption` и отрицательный `coalDelta`.
- `loyalty_rewards` уже содержит code, name, description, cost, visibility, active period, order и version.
- `loyalty_redemptions` уже содержит customer/reward snapshots, cost snapshot, idempotency key и статусы `pending`, `succeeded`, `canceled`, `reconciliation_required`.
- До M13.5 Loyalty service возвращал `redemptionEnabled=false`; Customer routes для rewards/redemptions отсутствовали.
- До M13.5 Customer UI показывал баланс и историю, но не предлагал списание.
- До M13.5 Admin UI показывал только read-only loyalty history; reward definitions не управлялись.
- Прототип упоминает соусы, напитки и скидки, но его reward values и economics являются demo-данными и не могут автоматически стать production contract.

## Owner Decision Gate

Owner decision received: first production reward is `fixed_discount`, applied to the next pickup order. MVP definitions are configured by Admin; each definition stores an integer `discountMinor` target and defaults to one claim per Customer. A claim expires at the definition `activeUntil`, or 30 days after redemption when no end is configured. Successful fulfillment is the atomic Backend confirmation that the claim was attached to a newly created `pending_payment` pickup order. No automatic reversal is introduced for cancellation/refund.

Решение закрывает исходный gate: разрешён один тип `fixed_discount`; Admin управляет definitions, угольки списываются при создании redemption, claim применяется максимум к одному следующему pickup-заказу, а отмена/refund не делает автоматический reverse.

## Scope

### Reward catalog

- Backend-owned reward definitions с отдельным `rewardType` и ссылкой на внутренний fulfillment target.
- Разрешать только утверждённые reward types; неизвестные type и target fail-closed.
- Integer `costCoal > 0`, bounded code/name/description, active period, visibility, order и version.
- Immutable snapshot code/name/type/cost/target в каждой redemption.
- Admin create/update/archive с optimistic version, idempotency и append-only definition history.
- Code нельзя менять после создания; физическое удаление reward definition запрещено.

### Customer redemption

Добавить защищённые Customer routes:

```text
GET  /loyalty/rewards
POST /loyalty/redemptions
GET  /loyalty/redemptions
GET  /loyalty/redemptions/:id
```

`POST` принимает только `rewardId` и использует `Idempotency-Key`. Customer не передаёт cost, balance, reward status, discount, product price или fulfillment result.

Backend перед списанием повторно проверяет:

- активную reward definition;
- срок действия и visibility;
- внутреннюю fulfillment target;
- balance и consistency loyalty account;
- лимит использования;
- совместимость с текущим order/checkout state, если reward применяется к заказу.

### Atomic debit and status

- Заблокировать `loyalty_accounts` через PostgreSQL row lock.
- Перечитать reward definition из Backend/PostgreSQL.
- Проверить достаточный баланс.
- Создать одну redemption с snapshot reward/cost.
- Создать один spent ledger entry с отрицательным integer `coalDelta`.
- Обновить aggregate account только в той же transaction.
- Повторить тот же запрос безопасно по idempotency key.
- Concurrent redemptions не могут потратить больше доступного баланса.
- Неуспешный/неизвестный fulfillment не становится `succeeded`.
- Не создавать второе списание при retry, reload, timeout или повторной доставке события.

Если fulfillment внутренний и подтверждаемый в рамках checkout/order flow, redemption остаётся `pending` до соответствующего Backend confirmation. При невозможности безопасно подтвердить результат используется `reconciliation_required`; автоматическое повторное списание запрещено.

### Admin reward management

Добавить защищённый Admin surface:

```text
GET   /admin/loyalty/rewards
POST  /admin/loyalty/rewards
PATCH /admin/loyalty/rewards/:id
```

Admin может изменять только definitions и их доступность. Запрещены:

- `set balance`;
- `set XP`;
- `set rank`;
- ручной debit/credit ledger;
- изменение или удаление прошлой redemption;
- подтверждение reward fulfillment в обход Backend evidence.

## Domain / Fulfillment Rules

- Customer session и ownership проверяются на Backend.
- Cost читается из текущей reward definition и сохраняется snapshot-ом.
- Изменение текущей reward definition не меняет уже созданную redemption.
- Reward не может быть выдан, если target неизвестен, скрыт, истёк, недоступен в каталоге или не прошёл iiko/checkout boundary.
- Каталог, цена и availability товара остаются Backend/iiko-owned; Customer input не является доказательством.
- Отмена/refund не делает автоматический обратный credit без отдельной утверждённой policy.
- При `pending`/`reconciliation_required` Customer видит понятный статус, но не success.
- Reward fulfillment не вызывает Push/SMS и не использует внешний provider без отдельного approved contract.

## Architecture / Constraints

- PostgreSQL + Backend — authoritative source для rewards, balances, redemptions и fulfillment state.
- Сохранять границу `contracts → repository → domain service → route → API client/controller → UI`.
- Все money/coal/cost/delta значения — integer units.
- Debit и spent ledger entry создаются атомарно.
- Aggregate balance не может стать отрицательным.
- Historical reward/cost snapshots immutable.
- Idempotency и row lock обязательны на redemption boundary.
- Unknown, stale, malformed, failed и reconciliation states не становятся success.
- Customer/Admin не передают и не утверждают server-owned cost, balance, reward status или fulfillment result.
- Миграции и ручная проверка используют только `vse_pro_zhar_dev`.

## Discoveries

- Loyalty schema already contains generic reward and redemption tables, but fulfillment type/target and public routes are not enabled.
- Existing ledger semantics already support a customer-owned spent redemption debit with negative coal delta.
- Prototype mentions sauces, drinks and discounts without a production fulfillment contract; those values require an explicit owner decision.
- A real reward cannot be represented by a successful UI toast alone; it must cross the existing checkout/order/iiko boundary or remain pending/reconciliation.
- `fixed_discount` can be fulfilled without a new provider: the discount is re-quoted from the immutable redemption snapshot and attached to the order through a transaction-local order snapshot.
- Existing `orders` records are kept backward-compatible; reward application history is stored in `loyalty_redemption_orders` so legacy order fixtures and snapshots do not gain fake defaults.
- Existing migrations were already applied through `0018`; `0019_m13_5_loyalty_rewards_redemption.sql` applies the target/snapshot/history additions without creating a second database.

## Decision Log

- Rewards remain Backend-owned; Customer never controls cost, balance or fulfillment status.
- First implementation must choose one concrete reward type before adding generic multi-provider abstractions.
- Redemption debit uses the existing append-only loyalty ledger and PostgreSQL account locking.
- No automatic balance reversal after cancellation/refund is added without a separate approved policy.
- No external provider or new infrastructure is added in this task.
- `fixed_discount` claims are single-use by default (`perCustomerUsageLimit = 1`), expire at `activeUntil` or after 30 days, and become `succeeded` when attached to a new pickup order before payment.
- Discount amounts are stored as integer RUB minor units; an order is rejected when the fixed discount exceeds the server-calculated subtotal.
