# M16.4 — Admin Promos

Status: completed
Milestone: M16.4
Depends on: M7 Orders, M8 Payment, M12 cancellation/refund boundary, M13 Loyalty rules, M16.2 Admin Customers

## Purpose

Добавить безопасный production-backed Promo vertical slice для Admin и, только после owner approval, для Customer checkout.

Promo rules влияют на деньги, поэтому M16.4 должен быть отдельным изолированным write-path:

```text
Admin promo definition
→ strict contract
→ protected route
→ PostgreSQL versioned definition
→ Backend promo validation
→ authoritative checkout quote
→ immutable order/promo snapshot
→ safe Admin/Customer presentation
```

Prototype demo promo logic нельзя переносить в production через localStorage, `data/store.json`, browser total или hardcoded codes.

## Mandatory Owner Decision Gate

Write-path implementation cannot start until these decisions are recorded in this plan.

### Promo types

Confirm:

1. `percent` discount allowed or not.
2. `fixed` RUB discount allowed or not.
3. `coal`/XP reward type allowed or not. Conservative baseline: **disabled** until reward/redemption contract exists.
4. Any other types.

Recommended initial production baseline: `percent` and `fixed` discounts only; `coal`, XP, physical prizes and promo-as-reward remain unavailable.

### Value and money rules

Confirm:

1. Percent bounds; recommended `1..100` integer percent.
2. Fixed discount currency; recommended RUB only.
3. Fixed discount maximum; it must never make total negative.
4. Minimum order amount in integer minor units.
5. Whether discount applies before/after any future fees or other adjustments.
6. Rounding rule for percent discount; recommended Backend integer floor.

### Validity and usage

Confirm:

1. Active period and timezone; recommended `Europe/Moscow`.
2. Global usage limit.
3. Per-Customer usage limit.
4. One use per order.
5. Whether usage is reserved at quote or consumed only at confirmed order/payment.
6. Behavior after payment failure, expiration, cancellation and refund.
7. Whether one order can use multiple promo codes; recommended no stacking.

### Customer experience

Confirm whether M16.4 includes Customer promo entry in cart/checkout. If not approved, Admin definitions can exist only as unavailable/not applied and no customer-facing fake input is added.

### Admin actions

Confirm:

- create;
- update future-facing fields;
- activate/deactivate;
- archive instead of destructive delete;
- see usage count;
- see redemption audit;
- export usage, subject to PII policy.

Recommended baseline: create/update/deactivate, immutable historical definitions and usage audit; destructive delete excluded.

## Approved production behavior after decision gate

### Definition

Minimum safe definition fields:

- stable code, normalized uppercase;
- description;
- type;
- integer value;
- minimum order total minor units;
- currency;
- activeFrom/activeUntil;
- global usage limit nullable;
- perCustomer usage limit nullable;
- stacking policy;
- active/visible state;
- version;
- created/updated timestamps;
- actor/audit fields where required.

### Quote

Backend validates promo in the same business boundary as checkout quote:

```text
authenticated Customer
→ current cart/catalog/availability validation
→ promo code normalization
→ active period check
→ min order check
→ usage limit check
→ discount calculation in integer units
→ final total recomputation
```

Customer total is never trusted. A stale quote, changed price, invalid promo or unavailable product invalidates the quote safely.

### Order snapshot

If promo application is approved, confirmed order must snapshot:

- promo definition ID/code/version;
- promo type/value;
- discount amount minor units;
- pre-discount and final totals;
- currency;
- safe usage/redemption source key.

Changing or deactivating a promo later must not rewrite historical order totals.

### Usage/idempotency

- Unique Customer/order/promo source key prevents duplicate usage.
- Concurrent requests cannot overspend a global or per-Customer usage limit.
- Retry of the same checkout/idempotency key returns the existing result.
- Failed payment/order creation does not consume usage unless the approved policy explicitly says it reserves usage.
- Unknown state becomes reconciliation/unavailable, never successful discount consumption.

## Scope

### Contracts

- Promo definition response/request schemas.
- Bounded Admin query/filter schemas.
- Promo usage/audit summary schema.
- Customer promo quote input/output only if approved.
- Safe errors: invalid code, inactive, expired, not started, minimum not met, limit reached, stacking forbidden, unavailable, reconciliation.
- Strict integer/percentage bounds and no client-authoritative totals.

### Database/repositories

- Versioned migration for definitions, usage/redemption and approved order snapshots.
- Constraints for code normalization, value bounds, active periods, currency, limits and statuses.
- Repository methods for list/create/update/deactivate definitions.
- Transaction-safe usage claim/check.
- Historical definition/value snapshots.
- Unique keys for idempotency/concurrency.
- Bounded pagination/search.

### Backend/domain/routes

- Protected Admin list/create/update/deactivate routes.
- Customer promo validation/quote route only after owner approval.
- Integration with existing checkout quote/creation boundary.
- Safe error mapping and request ID logging without sensitive data.
- No direct payment/provider calls from promo route.

### Clients/controllers/UI

- Shared Admin promo client/controller with runtime validation.
- Admin Promos screen matching prototype table/modal.
- Loading/empty/error/retry states.
- Customer promo input only if approved; it must reuse Backend quote and existing checkout lifecycle.
- Usage count from Backend only.
- Historical snapshot display is read-only.

## Out of Scope

- Promo-as-coal/XP reward until separate loyalty redemption contract.
- Physical prizes, discounts via external provider or marketing automation.
- Push/SMS/email dispatch.
- Multiple promo stacking unless explicitly approved.
- Delivery pricing/discounts while delivery is not production-supported.
- Admin balance/XP/rank setter.
- Destructive deletion of used definitions/history.
- New infrastructure or second database.

## Discoveries

- Prototype Promos contains table, modal, percent/fixed/coal types, minimum order field, active toggle, usage count and destructive delete.
- Current production has no promo definitions, promo repository, API, checkout promo input or usage ledger.
- M13 redemption/reward boundaries make prototype `coal` promo unsafe to enable automatically.
- M12 refund/cancellation policy must be included before a promo usage/discount path is declared complete.
- Admin definition writes are production-backed and versioned; because Customer checkout approval is not closed, no redemption claim, discount quote, order snapshot mutation or refund consumption is exposed in this task.
- Usage count is computed from persisted `promo_redemptions.status = 'succeeded'`; the Admin audit route exposes only bounded safe identifiers/amount snapshots and never source keys or raw provider data.
- The M16.4 Admin E2E set passed at `320`, `375`, `768`, and `1024`. A full 16-spec E2E run reached an existing staff login rate limit in unrelated Loyalty/Wheel specs; this does not affect the isolated Admin Promos spec.

## Decision Log

- M16.4 is isolated because promos affect money and checkout totals.
- Prototype visual composition is mandatory, but prototype codes/data/local logic are not production data.
- Recommended first production types are percent/fixed discounts only; coal/XP reward promotions remain unavailable until a separate approved reward contract.
- No Customer promo input or checkout mutation is implemented before owner approval of promo economics.
- No Push/SMS/email provider is part of M16.4.
- For this Admin-only slice, the task uses the conservative baseline from the plan: `percent` and `fixed` in RUB only; percent values `1..100`; fixed values and minimum order are integer minor units; percentage discount rounds down on the Backend; active period is `Europe/Moscow`; stacking is disabled; usage is counted only from persisted successful redemption rows; Customer checkout, usage claiming and refund consumption remain unavailable until a separate owner approval.

## Outcome

Implemented and verified the Admin-only M16.4 production slice: strict percent/fixed RUB promo definitions, PostgreSQL definition/version/redemption schema and repositories, staff-protected CRUD/lifecycle/audit routes, shared clients/controllers, and prototype-aligned responsive Admin UI. Customer checkout/promo application, coal/XP rewards, usage claiming and refund coupling remain explicitly unavailable pending a separate owner decision.
