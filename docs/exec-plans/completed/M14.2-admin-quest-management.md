# M14.2 — Полное управление Quest definitions в Admin

Status: completed
Milestone: M14.2
Depends on: M14 Wheel + Quests, M13 Loyalty, M11 Admin auth

## Purpose

Довести Admin-раздел «Квесты» до полноценного управления server-owned Quest definitions.

После задачи сотрудник сможет через Admin:

- создать новый квест;
- изменить название, описание, цель, период, награду и порядок;
- включить или выключить квест;
- безопасно архивировать квест без удаления его истории.

Customer по-прежнему только читает подтверждённый прогресс. Admin не меняет XP, угольки, progress, claims или ledger вручную.

## Current State

- PostgreSQL уже содержит `quest_definitions`, `quest_progress`, `quest_events` и `quest_reward_claims`.
- M14 seed содержит три квеста: `first_order`, `regular_guest`, `warming_up`.
- Backend имеет `GET /admin/loyalty/quests` и `PATCH /admin/loyalty/quests/:id`.
- Shared contract уже описывает `QuestDefinition` и update-поля.
- Shared Admin client умеет только читать список и менять `isVisible`/поля существующей definition.
- Admin UI показывает таблицу definitions и позволяет только «Скрыть/Показать».
- Физическое удаление опасно и не допускается: progress/events/claims имеют foreign keys на definition.

## Scope

### Quest definition lifecycle

- `GET` списка definitions оставить источником данных для Admin.
- Добавить создание definition.
- Добавить редактирование существующей definition.
- Добавить архивирование через `isVisible=false` и/или завершение `activeUntil`, без `DELETE`.
- Сохранять `version` и `updatedAt` при каждом изменении.
- Сохранять append-only snapshot изменений definition с Admin actor, action, version и request id.
- Не изменять исторические `quest_events`, `quest_reward_claims` и loyalty ledger после изменения definition.

### Разрешённая модель первой версии

Создание и редактирование ограничены уже утверждённой M14 моделью:

- `unit`: только `order` или `minor_units`;
- `rewardType`: только `xp` или `coal`;
- `goal`: целое положительное значение;
- `rewardValue`: целое положительное значение;
- `code`: lowercase `a-z`, цифры, `_`, `-`, 1–80 символов;
- `title`: непустой текст до 160 символов;
- `description`: до 2048 символов;
- `sortOrder`: целое неотрицательное значение;
- `activeFrom`/`activeUntil`: валидный период в timezone `Europe/Moscow`;
- repeatability: один claim на одного Customer для одной логической Quest definition;
- автоматический retroactive backfill не добавляется.

Код definition после создания неизменяем. Изменение `unit` после появления progress/events запрещено, чтобы не смешивать единицы измерения. Изменение goal не может сделать текущий progress больше goal. Reward type/value нельзя менять после создания claim; snapshots уже выданных claims остаются неизменными.

### API

Добавить защищённые Staff/Admin routes:

```text
GET   /admin/loyalty/quests
POST  /admin/loyalty/quests
PATCH /admin/loyalty/quests/:id
```

`PATCH` принимает `expectedVersion` и возвращает безопасный conflict при устаревшей версии. Создание использует `Idempotency-Key`, чтобы retry после timeout не создал второй квест. Отдельный destructive delete route не добавляется.

Ошибки должны маппиться в существующий safe envelope:

- 401/403 — auth/origin boundary;
- 400 — invalid code, fields, period, unit or reward;
- 404 — definition not found;
- 409 — duplicate code, stale version or forbidden change after progress/claim;
- 503 — database/reconciliation dependency unavailable.

Ошибки не возвращают SQL, stack trace, session token, provider payload или внутренние секреты.

### Contracts and API client

- Добавить strict `QuestDefinitionCreateRequestSchema`.
- Расширить update contract полем `expectedVersion`.
- Сохранять runtime validation всех create/update/list responses.
- Добавить методы `createQuest` и расширенный `updateQuest` в `AdminLoyaltyClient`.
- Контроллер Admin должен иметь loading, saving, retry, conflict, duplicate-code и unavailable states.
- Double-click и repeated submit должны быть безопасными и не создавать duplicate definition.

### Database and repository

- Добавить только versioned migration, если для append-only definition history не хватает существующей схемы.
- Не создавать вторую database, Redis, queue, worker или отдельный сервис.
- Repository owns parameterized queries, unique code constraint, version check and transaction boundary.
- Create/update/archive and audit snapshot are transactional.
- Existing foreign keys and immutable quest event/claim history remain intact.
- Existing three seed definitions сохраняются; migration не создаёт demo quests.

### Domain/service

- Проверять allowed units/reward types and integer bounds before repository write.
- Проверять active period and immutable code.
- Проверять ограничения изменения definition при существующем progress/event/claim.
- Не запускать processor, reward delivery или loyalty balance mutation из Admin update route.
- Changes apply only to future processing according to the approved M14 event boundary; historical events are not rewritten.

## Out of Scope

- списание угольков и каталог реальных rewards;
- promo/physical rewards;
- ручное изменение Customer progress, XP, угольков или rank;
- retroactive backfill исторических заказов;
- повторяемые/циклические quests и reset periods;
- новые criteria для segments или пользовательские сегменты;
- Push/SMS/email delivery;
- изменение Wheel settings или prize definitions;
- прямой доступ UI к PostgreSQL, iiko, YooKassa или provider;
- новая инфраструктура.

## Architecture / Constraints

- PostgreSQL + Backend — authoritative source для definitions, progress, events, claims и rewards.
- Сохранять границу `contracts → repository → domain service → route → API client/controller → UI`.
- Staff auth и safe origin обязательны для всех mutations.
- Все значения goal/reward/sort order — integer units; floating-point business calculations запрещены.
- Definition history, quest events, claims и ledger append-only там, где это требуется текущим M14 контрактом.
- Unknown, stale, malformed, unavailable и reconciliation states не становятся success.
- Customer/Admin UI не принимают client-provided progress, balance, reward или eligibility как truth.
- Миграции запускаются только против canonical `vse_pro_zhar_dev`.

## Tests

### Contract

- Reject unknown fields, empty code/title, invalid code and oversized text.
- Reject floats, zero/negative goal and reward, unsupported units/reward types and invalid periods.
- Validate `expectedVersion` and idempotency input.

### Repository/domain

- Create persists one definition and one audit snapshot.
- Repeated create with the same idempotency key returns one logical definition.
- Duplicate code returns safe conflict.
- Update increments version atomically and stale update returns conflict.
- Archive preserves definition, progress, events, claims and ledger history.
- Code remains immutable.
- Unit change is rejected after progress/events exist.
- Goal cannot become less than current progress.
- Reward change is rejected after claim exists.
- Existing three seed quests still process completed + paid order events exactly once.
- Processor retry/restart does not create duplicate progress or reward claims.

### API/security

- Anonymous Customer, anonymous Admin and Customer session receive 401.
- Staff session and safe origin are required for create/update/archive.
- No direct provider calls occur.
- Safe 400/404/409/503 responses contain no internal details.

### Admin UI/E2E

- Create, edit, hide/archive and reload definitions from Backend.
- Conflict state is visible and does not silently overwrite another update.
- Loading, empty, error, unavailable and validation states are explicit.
- Customer progress and loyalty balance remain read-only.
- Screenshots and no-overflow checks at `320`, `375`, `768`, `1024`.
- Modal keyboard focus, Escape, click-away and touch targets are checked.
- Existing Wheel, Loyalty, Orders, Customer and Admin shell scenarios do not regress.

## Discoveries

- Existing `quest_definitions` schema already has bounded fields, unique code, active period, visibility, sort order and version.
- Existing foreign keys make destructive Quest deletion unsafe; archive/deactivate is the correct lifecycle.
- Current Admin client/route supports only update, so create and optimistic version semantics are the primary missing boundaries.
- Existing `staff_audit_log` action constraint is limited to staff/order operations, so Quest definition snapshots use a dedicated `quest_definition_versions` table instead of mutating generic audit history.
- The canonical database already contained the three M14 seed definitions; migration `0017_m14_2_quest_definition_history.sql` adds only history storage and creates no quests.
- The existing Admin modal behavior helper already provides focus capture, Tab wrapping, Escape and click-away integration for the new Quest modal.

## Decision Log

- Пользовательские сегменты не входят в Quest task.
- Quest rewards remain limited to existing XP/coal ledger effects; promo and physical rewards stay out of scope.
- Admin manages definitions only; Customer progress and loyalty balances remain processor/ledger-owned.
- No new infrastructure is justified for this feature.
- Create idempotency is stored on the first definition snapshot with a payload fingerprint; retries return the existing definition without another snapshot, while duplicate code, stale version and history-protected changes use separate safe conflict codes.
- Quest periods are entered in the Admin UI as Europe/Moscow local time and sent to Backend with the explicit `+03:00` offset.
