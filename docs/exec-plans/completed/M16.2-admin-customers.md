## Approved M16.2 data contract

M16.2 is read-only and can proceed without a customer-editing decision gate.

Each list row may contain only:

- `id` — bounded positive server ID;
- `name` — approved display name;
- `phoneMasked` — Backend-masked phone;
- `orderCount` — count of Customer-owned orders from PostgreSQL;
- `spentMinor` — integer RUB minor units from approved qualifying order/payment facts;
- `coalBalance` — confirmed loyalty aggregate, nullable when unavailable;
- `xp` — confirmed loyalty aggregate, nullable when unavailable;
- `rank` — confirmed server-owned rank, nullable when loyalty is unavailable;
- `lastActivityAt` — nullable server timestamp from approved activity source.

Recommended baseline definitions:

- `orderCount`: count of Customer-owned persisted orders, without client-side reconstruction;
- `spentMinor`: sum of qualifying completed + provider-confirmed paid order totals; canceled/unpaid/unknown orders excluded;
- `coalBalance`/`xp`/`rank`: existing M13 loyalty service/repository boundary, never a separate calculation in Admin;
- `lastActivityAt`: latest approved server activity (`customer_sessions.last_used_at` or qualifying order activity, with exact source recorded in Decision Log); if no approved activity exists, return `null` and render `—`;
- default sort: `spentMinor DESC`, then `id ASC`, matching prototype's high-value-first behavior while keeping deterministic pagination;
- search: server-side normalized search over approved name and phone search boundary; raw phone must not be returned to UI;
- pagination: bounded `limit` and `offset`, maximum response size defined in contract.

If any definition is changed, update this plan before implementation.

## Scope

### Contracts

- `AdminCustomersQuerySchema` with bounded search, limit and offset.
- `AdminCustomerRowSchema` with masked PII and nullable loyalty fields.
- `AdminCustomersResponseSchema` with rows and pagination.
- Safe errors for unauthorized, validation, unavailable and reconciliation states.
- Strict schemas with no raw DB rows/provider payloads.

### Database/repository/domain

- Add `AdminCustomerRepository` query methods for bounded list/search/pagination.
- Join or aggregate only server-side from customers, orders, payments and loyalty projection/ledger boundaries.
- Reconcile loyalty aggregate through existing loyalty repository/service; do not duplicate rank calculation.
- Use deterministic ordering for stable pagination.
- Keep query result bounded and parameterized.
- Add indexes only when query plan/measurements justify them.
- No migration unless a verified query requirement needs one.

### API

- Protected `GET /admin/customers` or equivalent owner-approved route.
- Staff guard and existing safe-origin boundary.
- Runtime input parsing and output validation.
- No mutation routes in M16.2.
- No export route until explicit PII export approval; UI export action remains disabled/unavailable with truthful copy.

### API client/controller

- Shared Admin customer client.
- Runtime response validation.
- Loading/error/retry/abort/latest-request-wins lifecycle controller.
- Search resets offset to zero.
- Pagination actions preserve current search.
- No client-side filtering of an incomplete server result.

### Admin UI

- Enable Customers sidebar item only when the real screen is wired.
- Match prototype table and page header exactly.
- Render loading, error, empty/no-match and loyalty unavailable states.
- Render masked phone and integer money formatting.
- Render rank only from confirmed server response.
- Render pagination controls with accessible labels and disabled boundaries.
- Keep Export action visibly aligned with prototype but disabled/unavailable until approved.
- Preserve mobile sidebar/topbar and table overflow behavior.

## Out of Scope

- Customer detail CRM page.
