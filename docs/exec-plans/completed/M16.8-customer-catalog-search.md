# M16.8 — Customer Catalog Text Search

Status: completed
Milestone: M16
Depends on: M1 Catalog, M4 Cart, M13.2 Customer visual parity, M16.7 Admin Category Management

## Purpose

Добавить Customer возможность быстро находить блюдо по названию, описанию или названию категории.

Поиск работает по уже подтверждённому Backend каталогу и не становится источником истины для цены, видимости, availability или order state.

## Current State

- Customer Catalog показывает серверный каталог и фильтрует его только по категории.
- Admin Catalog уже имеет отдельный текстовый поиск.
- Catalog API не требует поискового query: для текущего масштаба один ресторан и небольшой каталог загруженный server snapshot фильтруется локально.
- Customer должен оставаться Expo/React Native compatible; нельзя использовать DOM-only search logic.
- Prototype visual language остаётся источником стиля, но search control добавляется как approved functional enhancement, потому что Product goal включает поиск блюда.

## Scope

- Search input с понятным accessibility label и placeholder.
- Case-insensitive Unicode-aware matching по `product.name`, `product.description` и названию видимой категории.
- Совместная работа с выбранной категорией.
- Очистка поиска без перезагрузки каталога.
- Отдельный empty state для «по запросу ничего не найдено».
- Loading/error states каталога не меняются.
- No API/DB schema changes, no fake data and no client price/availability logic.
- Responsive layout на `320`, `375`, `768`, `1024`, touch target минимум `44×44`.

## Out of Scope

- Full-text database search, ranking or server-side pagination.
- Search across orders, rewards or profile.
- Fuzzy/typo correction, synonyms and transliteration.
- Search hidden categories/products that Backend did not return.

## Architecture / Constraints

```text
Backend catalog snapshot → CatalogScreen local presentation filter → ProductCard
```

- Backend remains authoritative for catalog, price, visibility and availability.
- Search state is ephemeral UI state and is never sent as a business value to checkout/order/payment.
- Matching must be deterministic and safe for empty strings, Unicode and long input.
- The component remains native-safe and does not read DOM APIs.
- Existing prototype palette, spacing, typography and card language are preserved.

## Implementation Requirements

1. Add controlled search state to Customer `CatalogScreen`.
2. Add Unicode/case normalization helper and filter after category selection.
3. Add accessible input, clear action and no-results copy.
4. Keep cart, auth gate, checkout and server quote behaviour unchanged.
5. Add component and browser regression coverage.
6. Update product/QA documentation only after verification.

## Tests

- Empty query shows all products in the selected category.
- Name match is case-insensitive.
- Description/category match works.
- Search and category filters compose correctly.
- Unicode input does not throw or expose hidden products.
- No-match state is explicit and does not create an order/request.
- Clear action restores the current category results.
- Loading/error/retry remain unchanged.
- Responsive overflow and touch target checks pass at required widths.
- Existing full package and Playwright suites pass.

## Acceptance Criteria

- Customer can find a visible dish by text without reloading the catalog.
- Only products from the server-provided catalog are shown.
- Search never changes price, cart total, checkout or payment payloads.
- Accessibility label, keyboard/native input behaviour and clear action work.
- No horizontal overflow at `320/375/768/1024`.
- Full regression suite passes.

## Discoveries

- Backend уже возвращает достаточно данных для локального поиска; отдельный endpoint не нужен для текущего масштаба.
- Текущий Customer Catalog использует native-safe React state, поэтому поиск можно добавить без DOM-зависимости.
- Поиск проверяет только уже подтверждённые Backend products и категории; запрос не участвует в cart/checkout/payment payloads.

## Decision Log

- В первой версии поиск локальный по последнему подтверждённому каталогу; это уменьшает latency и не добавляет новую инфраструктуру.
- Поиск применяется поверх category filter, чтобы выбранная категория оставалась явным ограничением пользователя.
- Невидимые и отсутствующие в Backend товары никогда не попадают в результаты.
