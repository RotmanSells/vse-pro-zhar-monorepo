Status: completed

## Purpose

Выполнить следующий bounded visual-parity pass по Customer/Admin после прямого сравнения screenshot текущего приложения с `/Users/rotman/Desktop/prototypes`.

Результат задачи — существующие production screens визуально повторяют prototype настолько точно, насколько это возможно без добавления prototype-only business functionality.

## Mandatory Rules

Все правила ниже обязательны. Нарушение любого `MUST` означает, что задача не может быть отмечена completed.

### Prototype source of truth

- **🔴 MUST** — `/Users/rotman/Desktop/prototypes/index.html` является visual source of truth для Customer.
- **🔴 MUST** — `/Users/rotman/Desktop/prototypes/admin.html` является visual source of truth для Admin.
- **🔴 MUST** — до каждого UI-изменения изучить соответствующий prototype source и зафиксировать сравниваемый surface/state.
- **🔴 MUST** — точно переносить layout, header, tabbar/sidebar, typography, colors, gradients, glow, spacing, radii, shadows, cards, buttons, icon placement, active/disabled states и empty/loading/error states.
- **🔴 MUST** — запрещено самостоятельно придумывать альтернативный visual language или считать «похожее» достаточным без прямого screenshot comparison.
- **🔴 MUST** — любое намеренное визуальное отклонение от prototype записывается в `Decision Log` с причиной и owner approval.

### Functionality and source of truth

- **🔴 MUST** — переносить только существующую production functionality.
- **🔴 MUST** — prototype-only screens/features нельзя превращать в fake working functionality.
- **🔴 MUST** — если prototype-only element нужен для visual composition, он остаётся явно disabled/unavailable и не создаёт business side effects.
- **🔴 MUST** — нельзя добавлять fake XP, coal, rewards, quest progress, availability, prices, orders или customer data.
- **🔴 MUST** — Customer/Admin остаются presentation clients; Backend + PostgreSQL остаются источником истины.
- **🔴 MUST** — Backend/API/database/business logic не изменяются в рамках pure visual task.
- **🔴 MUST** — если visual parity требует нового API/business contract, остановиться и создать отдельную owner-approved task вместо скрытого изменения scope.

### Lego architecture

- **🔴 MUST** — сохранять lego boundaries:

  ```text
  contracts/types → API client → controller/lifecycle → screen UI → visual primitives
  ```

- **🔴 MUST** — UI не вызывает PostgreSQL, iiko, YooKassa или provider напрямую.
- **🔴 MUST** — UI не дублирует rank/eligibility/payment/order/availability state machine.
- **🔴 MUST** — переиспользовать существующие components, contracts, clients/controllers и platform adapters до создания новых.
- **🔴 MUST** — новые visual primitives должны иметь одну понятную ответственность и не смешивать transport/business state с layout.
- **🟡 SHOULD** — общие Customer visual tokens/components использовать одновременно на web/iOS/Android.

### Responsive and native app rules

- **🔴 MUST** — Customer остаётся Expo/React Native приложением с native iOS/Android targets; Web не превращается в WebView-first implementation.
- **🔴 MUST** — проверить widths `320`, `375`, `768`, `1024`.
- **🔴 MUST** — не допускать horizontal overflow, clipped controls или broken shell centering.
- **🔴 MUST** — interactive touch targets сохраняются минимум `44×44` px с минимум `8` px spacing.
- **🔴 MUST** — bottom tabbar/sidebar/header transformation соответствует prototype и естественен для touch input.
- **🟡 SHOULD** — проверять portrait/landscape tablet и on-screen keyboard для форм.

### Verification rules

- **🔴 MUST** — проверять loading, empty, error, unavailable, disabled и confirmed states.
- **🔴 MUST** — сохранить существующие accessibility labels, testIDs и working user flows.
- **🔴 MUST** — запускать `lint`, `typecheck`, tests и build после реализации.
- **🔴 MUST** — выполнить `git diff --check`.
- **🔴 MUST** — не объявлять visual parity completed только по прохождению tests; нужен screenshot/browser comparison с prototype.
- **🔴 MUST** — если screenshot comparison выявил существенное расхождение, исправить его до завершения task.

## Discoveries

- Prototype и production могут иметь одинаковую visual composition при разных наборах доступной business functionality; unavailable elements должны оставаться честными.
- Browser comparison подтвердил, что Customer сохраняет phone shell/header/category-chip/card/tabbar composition, а Admin — dark sidebar/table/card composition; prototype-only analytics, roulette, quests, profile и rewards не стали рабочими claims.
- Screenshot matrix: Customer menu + Passport and Admin catalog + Orders/Loyalty were checked against the matching prototype surfaces at 320, 375, 768 and 1024; state coverage included anonymous/current, empty/unavailable, secure-login and read-only views.
- Один residual responsive defect был фактическим: Admin logout control имел 37px ширины при 44px высоте; добавлен `min-width: 44px`, после чего Admin width matrix прошла.
- Expo dev-server подхватывает ignored Customer `.env.local`; test-only launcher временно изолирует этот файл и возвращает его после завершения, чтобы responsive/E2E evidence не зависела от developer API port.

## Decision Log

- Prototype exactness имеет приоритет над текущей самодельной UI-композицией.
- Functional scope остаётся ограничен production contracts; visual reference не расширяет business scope.
- Любое расхождение между visual parity и source-of-truth/lego правилами решается через отдельный owner decision, а не через скрытую логику в UI.
- E2E browser проверяется через same-host Customer API URL для корректной `SameSite=Lax` cookie semantics; production transport остаётся credentialed через Backend API boundary.
