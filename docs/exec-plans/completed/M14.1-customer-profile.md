# M14.1 — Customer Profile

Status: completed
Milestone: M14.1
Depends on: M5 Customer authentication, M7 Orders, M13 Loyalty, M14 Wheel + Quests local slice

## Purpose

Реализовать Customer Profile как полноценный production-backed экран, визуально и композиционно повторяющий Profile screen из prototype на 100%, но без переноса fake balances, hardcoded statistics, demo toggles или устаревшей loyalty economics.

Profile должен стать реальным вертикальным срезом:

```text
Customer Profile intent
→ shared contracts
→ authenticated API client/controller
→ Backend profile aggregation
→ PostgreSQL authoritative data
→ Customer Profile UI
→ browser/native verification
```

- **🔴 MUST** — prototype Profile является обязательным visual source of truth.

- **🔴 MUST** — Profile UI не вычисляет authoritative order count, favorite product, reward progress, balance, XP, rank или eligibility.
- **🔴 MUST** — не переносить demo values: `450` угольков, fake order count, fake favorite, `До след. награды = 3`, fake order history или local demo profile.

  ```text
  contracts → repositories → domain services → routes → API clients/controllers → Profile UI
  ```

- **🔴 MUST** — все monetary/XP/coal values остаются integer units.

- **🔴 MUST** — Customer видит только собственные данные.
- **🔴 MUST** — logout должен использовать существующий authenticated auth boundary, а не только очищать локальное состояние.

## Approved production behavior

### Identity

Profile показывает подтверждённые данные текущей Customer session:

- `name` — из Backend Customer profile;
- `phone` — при необходимости в безопасном masked/approved format;
- `birthDate` — только если уже разрешён существующим auth contract;
- декоративный avatar допускается как visual element, но не является fake identity proof.

Anonymous Customer не получает чужой или demo Profile. При открытии Profile без authenticated session используется существующий Customer identify flow; после отмены показывается безопасное unavailable/auth-required state.

### Stats

Profile API должен возвращать server-calculated stats:

- `orderCount` — количество Customer-owned orders по Backend source of truth;
- `favoriteProduct` — наиболее часто заказанный product по историческим `order_items` snapshots, nullable при отсутствии заказов;
- `nextMilestone` — nullable server-owned milestone, с безопасным `label`, `remaining`, `unit` и `source`;
- `coalBalance`, XP и rank — существующий подтверждённый M13 loyalty summary, без отдельного local duplicate.

Tie-break для favorite product должен быть детерминированным и записан в domain tests. Историческое имя берётся из order snapshot, а не из текущего каталога.

`nextMilestone` нельзя заполнять prototype number `3` по умолчанию. Если Backend не может безопасно определить следующий milestone, Profile показывает `—` или controlled unavailable state.

### Bonus information card

Композиция prototype сохраняется, но copy должна описывать только утверждённые production rules:

- XP: `1 XP` за каждый полный рубль завершённого оплаченного заказа;
- coal: `1 уголёк` за каждые полные `100 ₽`;
- rank thresholds: M13 server-owned `Искра`, `Жар`, `Пламя`, `Вулкан`;
- XP/coal не сгорают;
- Wheel: только approved M14 eligibility и только XP/coal/no-prize;
- Quests: только подтверждённые Backend definitions и progress;
- redemption, promo codes и physical rewards: явно недоступны, пока нет отдельного fulfillment contract.

Нельзя переносить prototype copy про `5%`, `1 XP за 10 ₽`, старые rank thresholds, `SPARK10`, `FIRE500`, `UGOL100`, бесплатные физические подарки или fake redemption.

Card должен иметь рабочее раскрытие/сворачивание без потери accessibility state и с корректным behavior на Web/native.

### Settings card

Prototype settings rows сохраняются визуально, но каждая функция обязана иметь честный production state:

- Push notifications — `unavailable/disabled`, пока M15 и native push contract не закрыты;
- Email subscription — `unavailable/disabled`, пока нет approved email provider/consent contract;
- Dark theme — не включать как fake business setting без owner-approved theme contract; если row сохраняется для visual parity, она должна быть clearly disabled/unavailable.

Нельзя делать toggle, который меняет только local state и выглядит как сохранённая server setting. Если owner отдельно утверждает конкретную setting mutation, для неё нужны contracts, persistence, auth, retry, failure state и tests.

### Order history

Profile показывает prototype-aligned recent order history:

- только собственные Customer orders;
- server-confirmed order snapshots;
- historical product names/prices;
- order date;
- pickup label/time;
- total в integer minor units;
- loading, empty, error и retry states;
- переход в существующий Orders/detail flow без дублирования business logic.

Если history card использует ограниченный recent list, должна быть явная кнопка/ссылка «Все заказы», открывающая существующий OrdersScreen.

### Logout

Logout вызывает существующий Backend auth logout boundary, после подтверждённого результата очищает local session representation и возвращает Customer в anonymous state. Ошибка logout не должна создавать ложное ощущение завершённой server session.

## Scope

### Contracts

- Strict `CustomerProfileResponse` или эквивалентный shared profile summary contract.
- Server-owned identity, stats, milestone, loyalty summary reference, settings availability и recent orders.
- Nullable fields для no-orders/no-favorite/no-milestone states.
- Bounded integer fields, safe text limits, strict enums и no provider payloads/secrets.
- Safe errors: authentication required, unavailable, reconciliation required, validation, timeout/network.

### Backend/repositories/domain

- Authenticated `GET /profile` или другой owner-approved Profile read route.
- Repository query для Customer-owned order count и favorite product по immutable snapshots.
- Domain service для deterministic stats aggregation и next milestone projection.
- Reuse existing loyalty/order/auth services; не дублировать rank, balance или order state machine.
- Safe handling for missing customer, stale/malformed snapshot, ledger reconciliation and unavailable dependencies.
- No new infrastructure and no second database.

### API client/controller

- Shared runtime-validated Profile API client.
- Lifecycle controller with loading/error/retry/abort/latest-request-wins behavior.
- Customer env/native adapters remain thin.
- No direct DOM API in shared business logic.

### Customer UI

- Enable Profile tab only when the actual Profile route/screen is ready.
- Add Profile screen within current Customer navigation.
- Match prototype Profile composition exactly.
- Render real identity, balance, stats, bonus rules, settings states, recent history and logout.
- Preserve current Menu, Cart, Checkout, Orders, Loyalty and Wheel behavior.
- Add accessibility labels, roles, focus/keyboard behavior for Web and native semantics.
- Support `320`, `375`, `768`, `1024` without overflow or clipped cards.

### Documentation

- Update this plan during implementation.
- Update `docs/PRODUCT.md` only if Profile becomes an approved durable product capability; do not silently change product scope.
- Record any setting kept disabled because M15/provider/owner contract is not ready.

## Out of Scope

- Push provider implementation and device token registration; belongs to M15.
- SMS provider implementation; belongs to M15.
- Email provider and marketing consent workflow without a separate approved contract.
- Dark theme system redesign without owner decision.
- Delivery workflow.
- Promo codes and coal redemption.
- Physical prize fulfillment.
- Direct loyalty balance/XP/rank editing.
- Rewriting order history or current catalog from Profile.
- Fake demo mode, fake rewards, fake stats or local-only authoritative state.
- New infrastructure, cache service, queue or second PostgreSQL database.

## Tests

### Contracts and domain

- Reject client-provided order count, favorite product, balance, XP, rank, milestone and settings status.
- Validate null/empty states.
- Validate integer bounds and minor units.
- Validate deterministic favorite product tie-break.
- Validate order count only includes Customer-owned orders.
- Validate historical snapshot usage after catalog rename/price change.
- Validate next milestone unavailable state when definitions/loyalty data cannot be confirmed.
- Ensure no provider payload, credentials or raw session data reaches Profile response.

### Backend/repository

- Authenticated Customer can read only own Profile.
- Anonymous Customer receives safe auth-required response.
- Foreign customer/order references cannot be used.
- Correct order count with zero, one and many orders.
- Correct favorite product with repeated products and ties.
- Correct empty history and missing favorite states.
- Correct loyalty summary and reconciliation/unavailable propagation.
- Correct recent order snapshots and pagination/limit behavior.
- Query does not read current catalog price/name for historical history.
- No write side effect is created by Profile GET.

### API client/controller

- Runtime parse success and malformed response rejection.

- Retry after failure.

## Decision Log

- Profile является extension существующего Customer visual world, а не новой visual identity.
- Prototype Profile обязателен для layout/style/spacing/states; production data и business rules берутся только из Backend.
- Stats и favorite product вычисляются Backend из Customer-owned orders и immutable order snapshots.
- Profile GET не создаёт ledger/order/reward side effects.
- Push, Email и Dark theme показываются только в truthful disabled/unavailable state до появления approved contracts; M15 не расширяется скрытой реализацией.
- Delivery, promo redemption, physical rewards и fake prototype values остаются out of scope.
- Profile read будет отдельным `GET /profile` с server-owned aggregate response; Customer UI не будет собирать stats из `/auth/me`, `/orders` или local storage.
- Recent history ограничивается сервером пятью последними заказами, но сохраняет order item snapshots; явная кнопка «Все заказы» возвращает в существующий OrdersScreen.
- Settings rows сохраняются для prototype parity как disabled/unavailable rows без local toggle state; redemption и physical rewards в Profile copy не появляются.
