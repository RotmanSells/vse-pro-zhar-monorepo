# M14.3 — Полное управление глобальными настройками Wheel в Admin

Status: completed
Milestone: M14.3
Depends on: M14 Wheel + Quests, M14.2 Admin Quest Management, M13 Loyalty, M11 Admin auth

## Purpose

Довести Admin-раздел «Колесо фортуны» до полноценного управления глобальными настройками Wheel.

После задачи сотрудник сможет через Admin:

- включить или выключить Wheel;
- изменить минимальную сумму подходящего заказа;
- изменить cooldown;
- изменить максимальное число вращений;
- изменить период, за который считается лимит;
- изменить общий активный период Wheel;
- увидеть, какое условие доступности действует сейчас.

Все изменения остаются server-owned, версионируются и не переписывают уже созданные spins, claims или loyalty ledger.

## Current State

- PostgreSQL уже содержит singleton `wheel_settings` с полями `enabled`, `eligibility`, `minOrderAmountMinor`, `currency`, `cooldownSeconds`, `maxSpins`, `limitPeriodSeconds`, `activeFrom`, `activeUntil` и `version`.
- Текущий M14 approved baseline: `completed_paid_order`, `150000` minor units, `86400` секунд cooldown, `1` spin, `86400` секунд limit period, `RUB`.
- Database constraints сейчас намеренно фиксируют eligibility, minimum, cooldown, max spins и period на этих значениях.
- Backend имеет `GET /admin/loyalty/wheel` и `PATCH /admin/loyalty/wheel/settings`, но update меняет только `enabled`, `activeFrom` и `activeUntil`.
- Shared `WheelSettingsUpdateRequestSchema` и Admin client также позволяют менять только `enabled` и активный период.
- Admin UI показывает minimum/cooldown/max spins карточками, но не позволяет их редактировать.
- Wheel prize definitions уже имеют отдельное управление и в M14.3 не переписываются.

## Scope

### Editable global settings

Сделать редактируемыми через одну атомарную настройку:

- `enabled` — включён или выключен;
- `minOrderAmountMinor` — минимальная сумма completed + paid заказа в integer minor units;
- `cooldownSeconds` — пауза между успешными вращениями;
- `maxSpins` — максимум успешных вращений одного Customer в периоде;
- `limitPeriodSeconds` — rolling period для `maxSpins`;
- `activeFrom` и `activeUntil` — период доступности Wheel.

`currency` остаётся только `RUB` и не редактируется.

`eligibility` остаётся `completed_paid_order`: условие должно быть видно в Admin как действующее, но режимы prototype `cart`, `customer_orders` и `always` не включаются без отдельного owner decision gate, потому что они меняют approved M14 business contract.

### Business semantics

- Eligible order остаётся только `completed` + provider-confirmed `succeeded` payment.
- Order total берётся только из Backend/PostgreSQL snapshot.
- `minOrderAmountMinor`, `cooldownSeconds`, `maxSpins` и `limitPeriodSeconds` не принимаются от Customer.
- Изменение settings применяется к будущим eligibility checks; прошлые spins/claims не пересчитываются и не изменяются.
- Если новая настройка делает состояние невалидным или не оставляет ни одного selectable prize, update отклоняется или возвращает explicit unavailable/reconciliation state.
- `maxSpins` должен учитываться корректно за rolling period, а не только по последнему spin.
- `cooldownSeconds` и `limitPeriodSeconds` не должны приводить к переполнению Date/number расчётов.

### Validation bounds

Все значения проверяются в shared contract, Backend и database. Минимальный технический baseline:

- `minOrderAmountMinor`: integer `>= 0`, safe PostgreSQL-compatible bound;
- `cooldownSeconds`: integer `> 0`;
- `maxSpins`: integer `> 0`;
- `limitPeriodSeconds`: integer `> 0`;
- `activeUntil` строго позже `activeFrom`, если обе даты заданы.

Перед реализацией owner должен зафиксировать product bounds для cooldown, period и max spins. Нельзя выбирать экономические лимиты только по удобству UI. До отдельного решения сохраняются текущие approved defaults: `150000 / 86400 / 1 / 86400`.

### Versioning, idempotency and audit

- Update принимает `expectedVersion` и возвращает safe `409 conflict` при устаревшей версии.
- Mutation использует `Idempotency-Key`; повтор после timeout возвращает известный результат и не создаёт второй settings change.
- Singleton row обновляется transactionally с row lock.
- Каждое изменение сохраняет append-only snapshot в `wheel_settings_versions`: все значения settings, actor, action, version, request id и timestamp.
- История spins, prize snapshots, reward claims и loyalty ledger не удаляются и не изменяются.
- Физическое удаление singleton settings запрещено.

## API

Сохранить существующий route и расширить его contract:

```text
GET   /admin/loyalty/wheel
PATCH /admin/loyalty/wheel/settings
```

`PATCH` принимает полный или частичный update, но Backend всегда валидирует итоговый полный snapshot settings. Payload не может менять `currency` или выбирать неподтверждённую eligibility.

Пример полей update:

```text
enabled
minOrderAmountMinor
cooldownSeconds
maxSpins
limitPeriodSeconds
activeFrom
activeUntil
expectedVersion
```

Safe error mapping:

- 401/403 — Staff auth/origin failure;
- 400 — invalid integer, date, range or unsupported field;
- 404 — settings singleton missing;
- 409 — stale version, idempotency conflict or invalid resulting configuration;
- 503 — database/reconciliation dependency unavailable.

Ошибки не раскрывают SQL, stack trace, credentials, session token или provider payload.

## Architecture / Constraints

- Сохранять границу `contracts → repository → domain service → route → API client/controller → UI`.
- PostgreSQL + Backend — единственный источник истины для Wheel settings и eligibility.
- Staff auth и safe origin обязательны для mutation.
- Все деньги и лимиты хранятся как integer units.
- UI не обращается напрямую к PostgreSQL, iiko, YooKassa или provider.
- Unknown, stale, malformed, failed и reconciliation states не становятся success.
- Нельзя ослаблять M14 approved eligibility через prototype demo controls.
- Новая инфраструктура не нужна: достаточно текущей PostgreSQL и modular monolith.
- Изменение settings не должно вручную выдавать XP/угольки, создавать spin или менять claims.

## Discoveries

- Existing `wheel_settings` already stores all prototype settings but database checks currently pin the approved M14 baseline.
- Current repository and client update only `enabled` and active period.
- Rolling `maxSpins` is not equivalent to checking only the latest spin; configurable limits require a count/window query.
- `wheel_settings` is a singleton and can be safely updated with a row lock in the existing PostgreSQL transaction model.
- No separate product decision document defines economic upper bounds for the editable limits; M14.3 therefore keeps the approved baseline values and uses the existing PostgreSQL-compatible technical bounds (`minOrderAmountMinor` 0..2147483647, the three positive integer limits 1..2147483647) without introducing new economic policy.
- The prototype exposes unsupported eligibility modes, so the Admin form will render the server-owned `completed_paid_order` condition as read-only.
- The new history table starts recording from the first M14.3 mutation; the pre-existing baseline row is preserved without inventing an actor or synthetic audit event.
- Existing Customer/Admin Wheel e2e expectations used fixed baseline copy; the UI now derives the copy from Backend settings while retaining the approved baseline wording.

## Decision Log

- M14.3 does not add new reward types, prize definitions or delivery behavior.
- Eligibility remains `completed_paid_order`; unsafe prototype modes stay unavailable until a separate owner decision.
- Settings changes apply prospectively and preserve immutable spin/claim/ledger history.
- No Redis, queue, worker or second database is required.
- Editable limit validation uses the current PostgreSQL integer range as a technical safety boundary; default economics remain `150000 / 86400 / 1 / 86400` until an owner decision changes them.
- The Admin mutation uses a server-computed request fingerprint for the `Idempotency-Key`; retries with the same key return the recorded snapshot before optimistic-version checks.
