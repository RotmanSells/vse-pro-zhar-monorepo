If the gate is not closed, keep write controls unavailable and implement only read/preview states without fake persisted delivery records.

## Recommended production baseline

### Templates

Templates are server-owned definitions with stable code, title, safe body and allowed variables. Prototype copy is only a visual/content reference; no fake promo codes, random names, random discounts, fake orders or fake coal values may be substituted into production.

Recommended safe variable set:

- `{name}` from approved Customer display name;
- `{order}` only when a real order reference is selected;
- `{promo}` only when an approved active Promo definition is selected;
- `{date}` generated by Backend timezone rules;
- `{dish}` only from an authoritative catalog product;
- `{coal}` only from confirmed loyalty summary.

Unknown or unavailable variable data must produce a validation/unavailable state, not a guessed value.

### Draft

Draft fields:

- stable ID;
- title/template code;
- bounded body;
- target segment ID/version;
- preview recipient count/time;
- channel state;
- optional approved promo reference/version;
- optional schedule metadata;
- status `draft` or `previewed`;
- actor and timestamps;
- version for optimistic concurrency.

No `sent`, `delivered` or `read` status is valid in M16.5.

### Audience preview

- Segment membership comes from M16.3 Backend query.
- Count is calculated server-side.
- Preview returns bounded masked rows only.
- Preview has `generatedAt` and segment definition version.
- A changed segment definition invalidates an old preview.
- Audience preview does not reserve, send or mutate customer data.

### Idempotency

- Repeated draft save with the same idempotency key returns the same draft.
- Concurrent edits detect version conflict and never silently overwrite newer text.
- Repeated preview does not create duplicate history or recipient rows.
- No provider retry loop exists in M16.5.

## Discoveries

- Prototype contains a message composer modal, six templates, segment recipient preview, optional promo attachment, preview action, send action and message history page.
- Prototype message values and delivery history are local/demo and cannot be used as production truth.
- M16.3 provides the required future segment audience boundary; M16.4 provides the future promo definition boundary.
- Push/SMS delivery is intentionally deferred to M15.
- Current M16.3 implementation already exposes protected built-in segment list/preview with bounded masked rows; Communications must reuse it rather than calculate audience membership.
- M16.4 currently exposes only approved `percent`/`fixed` promo definitions; attachment must remain unavailable until the M16.5 draft gate is approved.
- The existing staff login limiter allows 10 attempts per 15 minutes per IP; the full 17-test E2E suite exceeds it when run serially, while the isolated Communications E2E passes.

## Decision Log

- M16.5 implements preparation only; actual notification delivery remains M15.
- Prototype layout and interaction composition are mandatory, while fake message statuses and recipients are forbidden.
- Send and PII export remain disabled/unavailable until their separate contracts are approved.
- Segment preview must be server-owned and bounded.
- Until the owner gate is explicitly approved, implement Backend-owned template definitions, protected segment preview reuse, an empty server-owned history response and explicit unavailable draft/save/send/export controls. Do not create a persistence migration or delivery-like history table.
- The persistence gate was subsequently approved and implemented in M16.5.1; this predecessor remains the read/preview foundation, while persisted draft/history behavior is tracked by that continuation plan.
