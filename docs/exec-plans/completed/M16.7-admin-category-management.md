# M16.7 — Admin Category Management

Status: completed
Milestone: M16
Depends on: M1 Catalog, M11 Admin Orders, M16.6 Admin Integration / Visual Parity

## Purpose

Добавить в Admin полноценное управление категориями меню через Backend и PostgreSQL.

Admin должен уметь:

- создавать категорию;
- редактировать название и описание, если описание будет добавлено в approved contract;
- менять порядок категорий;
- скрывать и возвращать категорию в меню;
- видеть количество блюд и текущий статус категории;
- безопасно повторять запрос после timeout или reload.

Customer должен видеть только подтверждённые Backend категории и блюда из видимых категорий.

Физическое удаление категории не добавляется: категория архивируется/скрывается, чтобы не ломать исторические заказы и связи с Product.

## Current State

- Admin раздел `Меню` уже показывает каталог блюд, фильтр по категории и выбирает категорию при создании/редактировании Product.
- Backend уже имеет `POST /admin/categories` и `PATCH /admin/categories/:id`.
- Catalog repository уже хранит `slug`, `name`, `sortOrder`, `isVisible`, `createdAt`, `updatedAt`.
- В текущем Admin UI нет отдельной таблицы, модального окна или controls для управления самими категориями.
- У текущих category mutations нет полноценной idempotency/version-locking/audit boundary, сопоставимой с Quest, Reward и Wheel settings mutations.
- Product → Category защищён foreign key с `ON DELETE RESTRICT`; удаление категории не должно обходить это ограничение.
- Customer catalog исключает скрытые категории; отсутствие или повреждение category mapping не должно делать Product доступным.
- Используется только canonical PostgreSQL database `vse_pro_zhar_dev`.
- Prototype `/Users/rotman/Desktop/prototypes/admin.html` показывает категорийный контекст внутри раздела Menu, но не является источником фиктивных category records.

## Scope

### Admin UI

Добавить в существующий раздел `Меню` отдельный visual block «Категории меню»:

- список категорий в server-owned порядке;
- название, slug, количество блюд, порядок и статус;
- кнопка `Добавить категорию`;
- редактирование категории в modal/dialog;
- переключатель видимости;
- controls изменения порядка;
- явный статус сохранения, ошибки, conflict и unavailable;
- confirmation перед скрытием категории, если в ней есть видимые блюда;
- archive/hide вместо DELETE;
- закрытие modal по Escape и click-away;
- focus return/focus trap и `body { overflow: hidden }` во время modal;
- responsive behaviour и touch targets минимум `44×44` на `320`, `375`, `768`, `1024`.

Существующий Product editor сохраняет выбор категории и не получает прямой доступ к базе.

### Backend/API

Сохранить существующие endpoints, но усилить их контрактами:

```text
POST  /admin/categories
PATCH /admin/categories/:id
```

Оба mutation endpoint должны:

- требовать Staff session;
- проверять безопасный Origin для cookie mutation;
- принимать только strict validated fields;
- требовать `Idempotency-Key`;
- возвращать server-owned category response;
- возвращать безопасные conflict/error codes;
- не принимать `productCount`, `isVisible`, `version`, `slug` или timestamps как неподтверждённые computed values;
- не раскрывать SQL, stack trace, secrets или лишние PII.

Для update добавить `expectedVersion`. Slug после создания считается immutable; изменение отображаемого имени и порядка не должно менять исторические Order snapshots.

Если для reorder потребуется отдельный bulk endpoint, он добавляется только после подтверждения API-контракта. В первом срезе допустим bounded update отдельных категорий с integer `sortOrder`.

### PostgreSQL/repository

Добавить versioned migration только в canonical database:

- `categories.version` с положительным integer constraint;
- append-only `category_versions` для create/update/archive audit snapshot;
- actor Staff, request ID, idempotency key и payload fingerprint;
- unique `(category_id, version)` и unique idempotency key;
- checks для slug, name, sort order, version и action;
- сохранение существующих Product foreign keys и Order history;
- отсутствие destructive delete.

Repository должен использовать row lock и optimistic version check:

- повтор того же idempotency key возвращает известный результат;
- тот же key с другим payload даёт idempotency conflict;
- stale `expectedVersion` даёт version conflict;
- concurrent updates не перетирают более новую версию;
- изменение категории не переписывает Product snapshots в исторических Order.

### Customer/catalog behaviour

Проверить, что:

- скрытая категория не появляется в public `/catalog`;
- Product из скрытой категории не появляется в Customer;
- прямой reference на Product из скрытой категории не проходит quote/checkout/order;
- возвращение категории в видимость отражается после нового Backend read;
- Admin продолжает видеть hidden categories и их блюда;
- Customer UI не вычисляет category availability самостоятельно.

## Out of Scope

- синхронизация категорий из iiko;
- импорт названий, цен или изображений из iiko;
- удаление категории через DELETE;
- массовое перемещение всех блюд без отдельного UI/contract decision;
- пользовательские сегменты;
- изменение визуального языка, не соответствующее Admin prototype;
- прямой доступ Admin UI к PostgreSQL;
- новая база, Redis, очередь, отдельный сервис или event bus.

## Architecture / Constraints

Сохраняется граница:

```text
contracts → catalog repository → Backend route → Admin API client → Admin screen
```

- Backend + PostgreSQL — источник истины для category name, slug, visibility и order.
- Admin UI — только представление подтверждённого состояния.
- Все mutation values проходят runtime validation.
- `sortOrder`, `version` и counters — integer values; client-provided count не является authoritative.
- Product availability остаётся отдельной от category visibility: category visibility не заменяет iiko availability.
- Исторические Order snapshots не читают текущее имя категории для восстановления прошлого заказа.
- Все локальные проверки используют `vse_pro_zhar_dev`.
- E2E запускается одним worker, потому что mutations используют общую persistent canonical DB.
- Prototype-only demo categories не seed-ятся автоматически.

## Discoveries

- Existing category POST/PATCH API is present, but the Admin screen currently exposes only a category filter and Product form selector.
- Categories are already protected by Product foreign keys with restrict-on-delete semantics.
- Public catalog filtering already treats category visibility as a separate Backend-owned boundary; the new UI must preserve that behaviour.
- Public `CatalogResponse` intentionally remains free of Admin audit metadata, so the server-backed category table uses a dedicated Staff-protected `GET /admin/categories` response with version, timestamps and product count.
- Existing categories receive `version = 1` in the sequential migration; audit snapshots start with the first mutation performed after that migration, while newly created categories write their `created` snapshot atomically.
- Browser runtime exposed that `crypto.randomUUID` must be called with its crypto object as receiver; the Admin/client fallback now preserves that binding.

## Decision Log

- Category management lives inside the existing Admin `Меню` section; no new sidebar item is needed.
- Hide/archive is the only removal model for categories; historical Product and Order data must remain addressable.
- Slug is immutable after creation in the first slice; display name, visibility and sort order are editable.
- No iiko category ownership is introduced; iiko remains only the operational availability boundary.
- Category reordering uses bounded per-category `sortOrder` updates; a separate bulk reorder contract is not introduced for the first slice.
- Idempotency is carried in the `Idempotency-Key` header and payload fingerprints are computed by Backend from the strict normalized body; clients can reuse an explicit key for timeout retry.
