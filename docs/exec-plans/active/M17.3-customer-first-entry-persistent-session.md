# Customer first entry and persistent session

Status: in_progress
Milestone: M17
Depends on: M15.1 phone-only auth, M17.2 development action logging

## Purpose

Сделать первый вход Customer полноценным созданием/восстановлением профиля: пользователь один раз вводит имя и номер телефона, по желанию дату рождения, после чего профиль сохраняется в PostgreSQL, а bearer-сессия сохраняется на устройстве и восстанавливается после перезапуска приложения.

## Current State

- `customers` уже содержит `phone`, `name`, `birth_date` и уникальность номера.
- `customer_sessions` уже хранит hash токена, срок действия, revoke и last-used timestamps.
- Backend `POST /auth/identify` делает upsert Customer и создаёт новую сессию.
- Customer получает имя только в контекстных modal-gates; первый запуск не требует заполнения профиля.
- Native transport использует SecureStore, а Expo Go development fallback теперь общий для всех API-клиентов.
- Значение по умолчанию для customer session — 30 дней; требование задачи — не разлогинивать активного пользователя.

## Scope

- Первый экран/вход Customer показывает обязательные имя и номер телефона и необязательное поле даты рождения.
- Backend принимает и валидирует эти данные, сохраняет их в `customers`, не затирает уже сохранённую необязательную дату при повторном восстановлении.
- После успешной регистрации/восстановления native token сохраняется в SecureStore, web-сессия продолжает работать через cookie.
- При последующем запуске приложение сначала восстанавливает сессию и не показывает форму повторно при действительной сессии.
- Customer UI не выполняет автоматический logout; ручное завершение сессии не является частью обычного пользовательского потока.
- Добавляются automated tests для first-entry form, persistence, rehydration и повторного запуска.

## Out of Scope

- SMS-коды, password auth, email auth и verification provider.
- Изменение loyalty, payments, iiko, push/SMS delivery или Admin auth.
- Удаление исторических Customer или session records.
- Новая база, Redis, очередь или отдельный auth service.

## Architecture / Constraints

- PostgreSQL + Backend — источник истины Customer и session.
- Телефон нормализуется и проверяется Backend; клиентские значения не являются доказательством валидности.
- Токен не логируется и не попадает в response-body logs; на native он хранится только через SecureStore.
- Сессия имеет long-lived/sliding expiry в пределах безопасного серверного TTL; просроченный или отозванный токен снова приводит к форме входа.
- Все изменения схемы, если понадобятся, выполняются versioned migration; текущих полей для задачи достаточно.
- Сохраняются lego boundaries: contracts → API client/controller → Customer UI.

## Implementation Requirements

- `CustomerIdentifyRequestSchema` явно описывает имя, телефон и nullable/optional дату рождения.
- `CustomerIdentifyModal` получает режим first-entry и не позволяет пропустить обязательные поля; дата проверяется в понятном формате.
- `CatalogScreen` открывает first-entry flow после anonymous hydration и не блокирует действующую identified session повторным modal.
- Repository upsert сохраняет существующую birth date, если новая дата не передана.
- Default customer TTL увеличивается до долгоживущего значения, а обращение к активной сессии продлевает expiry.
- Тесты покрывают повторный reload, invalid input, missing token, expired token и сохранение профиля.

## Tests

- Contracts: required name, phone normalization boundary, nullable/optional date and invalid/future dates.
- API/repository: customer insert, existing customer update, preserved optional date and session rehydration.
- Customer: first-entry render, validation, submit payload and no repeat prompt for identified state.
- Existing full unit/integration suite, typecheck, lint, build and Playwright Customer auth flow.
- Manual Expo Go check: fill form once, reload app, close/reopen Expo Go session and verify profile remains identified.

## Acceptance Criteria

- На чистом Customer запуске форма просит имя и номер; дату рождения можно пропустить.
- После сохранения запись существует в canonical `vse_pro_zhar_dev`, а Customer получает active session.
- После reload/перезапуска действительная session восстанавливается без повторного ввода.
- `/auth/me`, profile, loyalty и cart requests после восстановления получают `200`, а не `401`.
- Недействительная/просроченная session не приводит к бесконечному циклу запросов и безопасно возвращает first-entry flow.
- Automated checks проходят, план содержит фактический Outcome и переносится в `completed/` только после verification.

## Discoveries

- Схема PostgreSQL уже содержит необходимые поля `customers.birth_date` и `customer_sessions`; новая migration для базового профиля не нужна.
- До задачи форма открывалась только при попытке добавить товар/открыть loyalty/cart, поэтому пользователь мог иметь товары в guest cart без Customer profile.
- Expo Go ранее терял токен между разными API-клиентами из-за раздельного fallback closure; это исправлено отдельным commit `bc73ab1`.
- Полный browser E2E после перехода на first-entry прошёл `22/22`; cold Expo Web bundle может занимать больше минуты и не является ошибкой приложения.
- В момент мобильного сбоя Backend не получил запросов: Metro записал сетевой `fetch failed`, а LAN `/health` оставался `200`; это был разрыв соединения Expo Go с локальной сетью, а не потеря Customer session.

## Decision Log

- Первый entry реализуется поверх существующего `/auth/identify`, чтобы не создавать вторую auth-модель.
- Имя обязательно для нового Customer; дата рождения остаётся добровольной и nullable.
- Ручной logout оставляется только как технический API boundary/отдельная recovery action, но убирается из обычного first-entry UX, чтобы приложение само не завершало сессию.

## Outcome

Реализованы first-entry поля имени, телефона и необязательной даты рождения, Backend persistence в `customers`, native SecureStore session и годовой customer TTL. Customer UI больше не содержит logout-действий, которые могли случайно завершить сессию. Automated и browser verification пройдены; ручной контроль на подключённом Expo Go устройстве остаётся последним незавершённым пунктом перед переносом плана в `completed/`.
