# M15.2 — Real Push delivery

Status: in_progress
Milestone: M15
Depends on: M15 native Push registration, M16.5.1 communications persistence

## Purpose

Подключить реальную доставку Push на зарегистрированное устройство Customer через Expo Push Service и дать Admin безопасный проверочный сценарий на один номер телефона.

## Current State

- Native Customer получает Expo Push Token после permission и регистрирует его через `/notifications/devices`.
- Backend хранит устройства и Push preferences в PostgreSQL.
- Admin Communications пока оставляет dispatch unavailable.
- Expo рекомендует отправлять с Backend на `https://exp.host/--/api/v2/push/send`, получать ticket и проверять receipt; `ok` ticket означает приём Expo, а не гарантированное отображение на устройстве.
- Пользовательские сегменты не входят в scope по решению owner.

## Scope

- Server-side Expo Push provider adapter с timeout, runtime validation, safe error mapping и optional access token.
- PostgreSQL delivery records: request fingerprint, device, provider ticket, status, error code и timestamps.
- Protected Admin `POST /admin/notifications/push` for one normalized phone number, title and body.
- Idempotency: повтор одинакового request не создаёт вторую доставку; другой payload с тем же key даёт safe conflict.
- `DeviceNotRegistered` disables the device; provider/network uncertainty becomes reconciliation-required.
- Admin Customer UI panel for a single-device test Push and truthful accepted/failed/unavailable states.
- Native registration/foreground presentation logs and documentation for APK/EAS credentials.

## Out of Scope

- Mass campaigns, custom/user segments, scheduling and marketing automation.
- SMS delivery and login codes.
- Direct FCM/APNs implementation instead of the existing Expo Push boundary.
- Automatic order/loyalty transactional templates.
- Sending a real notification during automated tests.

## Architecture / Constraints

- Backend + PostgreSQL remain authoritative; Admin never sends directly to Expo from the browser.
- Only enabled devices of the explicitly normalized target Customer are eligible.
- Raw Expo token stays server-side; Admin response contains ticket/status, never token or provider payload.
- Delivery statuses distinguish `accepted` (Expo ticket) from `delivered` (provider receipt) and `reconciliation_required`.
- No Redis, queue, microservice or second database; delivery writes use the existing PostgreSQL transaction boundary.
- All external provider calls are isolated behind an injectable adapter and use bounded request size/timeouts.

## Implementation Requirements

- Strict contracts → API client → Admin UI; repository/domain/provider separation.
- Versioned migration for delivery persistence.
- Provider response and receipt schemas validated at runtime.
- `Idempotency-Key` required on Admin send.
- The send endpoint must return no-device and push-disabled states without calling Expo.
- A stale/replayed key must not issue another provider request.

## Tests

- Expo provider success, ticket error, HTTP error, timeout and malformed response.
- Repository delivery idempotency, fingerprint conflict and device disable.
- API auth/origin/idempotency/no-device/push-disabled/success/error mapping.
- API client and Admin form validation/result states.
- Full package tests, canonical migration/probe, E2E, lint, typecheck, build and audit.
- Manual Android APK check with notification permission enabled and app backgrounded.

## Acceptance Criteria

- Admin can enter one phone, title and body and receive a real Push on its registered Android device after provider/EAS setup.
- The Backend, not browser, calls Expo Push Service.
- Duplicate request key does not send duplicate provider messages.
- Invalid/unregistered devices are disabled and never repeatedly targeted.
- Provider uncertainty is visible as reconciliation-required, never as delivered.
- No user segment or raw device token is exposed.

## Discoveries

- Existing M15 implementation registers devices but deliberately does not send messages.
- Expo's current documentation states that remote notifications are unavailable in Expo Go on Android from SDK 53; a development/preview APK is required for a real Android receipt.
- The first browser E2E attempt caught a Vite-only runtime crash from using Node `process.env`; the Admin Push wrapper now uses `import.meta.env` and the full 22-test E2E passes.
- Canonical migration verification found an existing unrelated `schema_migrations` table; the integration assertion now checks required project tables without deleting external data.
- Automated verification completed with 52 contract tests, 86 API-client tests, 123 API tests, 29 Customer tests, 20 Admin tests, 25 PostgreSQL tests and 22/22 Playwright tests; build, lint, typecheck and audit also pass.

## Decision Log

- Use a single-device phone-targeted test endpoint first because owner does not need user segments and this avoids accidental broadcast.
- Reuse Expo Push Service rather than introducing direct FCM/APNs adapters for the first real delivery checkpoint.
- Persist provider ticket/status metadata without raw provider payloads or device tokens in Admin responses.

## Outcome

Реализованы Expo Push provider, single-device protected Admin send route, delivery persistence, idempotency conflict handling, dead-device disable и Admin форма «Проверочный Push». Automated checks проходят: package tests 52 contracts, 86 api-client, 123 API, 29 Customer, 20 Admin и 25 PostgreSQL; Playwright 22/22; typecheck, lint, build, audit и migration/probe. Реальная доставка на Android ещё не подтверждена: требуется preview/development APK, EAS project/FCM credentials, public Backend URL и ручной receipt на устройстве.
