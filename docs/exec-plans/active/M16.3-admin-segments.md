## Segment Definition Gate

Before implementing custom segment write-path, confirm and record:

1. **Live vs snapshot:** recommended baseline is live server query; a segment count changes when authoritative data changes.
2. **Timezone:** recommended `Europe/Moscow` for inactivity/activity criteria.
3. **Supported built-ins:** exact names, descriptions, criteria and thresholds.
4. **Supported custom criteria:** exact operators, units and maximum values.
5. **Membership semantics:** whether canceled/unpaid orders count; recommended baseline uses completed paid orders for spend/order-based criteria.
6. **Activity semantics:** exact source for `lastActivityAt`; unknown activity must not qualify as active/inactive.
7. **Loyalty semantics:** coal/rank conditions use confirmed M13 account only; reconciliation-required accounts are excluded or shown unavailable, never guessed.
8. **Preview limit:** maximum customer rows returned in a detail preview.
9. **PII export:** whether CSV export is allowed. Default is disabled/unavailable.
10. **Message preview:** whether a segment can be selected by future message draft UI. It must not send anything in M16.3.
11. **Custom lifecycle:** create, update, deactivate, archive or delete. Recommended baseline is create/update/deactivate with immutable definition history; destructive delete is excluded.

If the gate is not approved, implement built-in read-only cards and a truthful unavailable state for custom segment mutations.

## Recommended production baseline

### Built-in segments

Use server-owned definitions with stable codes and explicit criteria. Recommended initial set, subject to owner confirmation:

- `sleeping` — no qualifying completed paid order for at least 30 days;
- `one_timer` — exactly 1 qualifying completed paid order;
- `churned` — no qualifying order for 14–30 days;
- `newbies` — first qualifying order within the last 7 days;
- `regulars` — at least 3 qualifying completed paid orders;
- `vip` — at least 5 000 ₽ qualifying spend;
- `big_spenders` — average qualifying check at least 1 500 ₽;
- `coal_rich` — confirmed coal balance at least 300;
- `at_risk` — no qualifying order for 7–14 days after prior activity.

Prototype thresholds are candidates, not automatically approved production economics. They must be recorded as owner-approved definitions before write-path/seed.

### Custom segments

Recommended supported criteria:

- orders `>=` / `<=` integer count;
- qualifying spend `>=` / `<=` integer RUB minor units;
- inactive days `>=` integer days;
- active days `<=` integer days;
- confirmed coal balance `>=` integer units;
- average qualifying check `>=` integer minor units.

Every criterion must be represented as strict typed data, not arbitrary SQL or an expression supplied by the browser.

## Discoveries

- Prototype page includes built-in segment cards, custom segment table, detail panel, creation modal, message action and CSV export action.
- Prototype segment membership is calculated from local demo Customer arrays and must be replaced by server-owned queries.
- M16.2 provides the required protected/masked Customer data boundary.
- Push/SMS and message delivery must remain outside M16.3.
- Canonical `vse_pro_zhar_dev` contains loyalty accounts requiring reconciliation; `coal_rich` therefore fails closed instead of exposing a guessed count.
- Existing Admin CSS already defines the prototype visual language and responsive navigation; Segments inherits it without a new design system.

## Decision Log

- M16.3 is a separate segmentation slice and does not implement Promotions or message delivery.
- Prototype layout is mandatory; prototype customer arrays and local segment logic are forbidden in production.
- Recommended baseline is live Backend query/projection with Europe/Moscow criteria evaluation.
- PII export and message actions remain unavailable until separate approved contracts.
- Implemented the safe read-only subset as built-ins plus bounded preview; custom definitions remain an explicit `owner_decision_required` unavailable state, so no custom schema migration or write route was introduced.
- Built-in counts use completed + succeeded RUB orders with exact amount/currency binding and exclude active refunds; loyalty membership uses a ledger-consistent M13 account only.
- Inactivity and recency boundaries are evaluated by Europe/Moscow local calendar date; preview is capped at 50 rows and ordered by spend descending, then customer id ascending.
- Segment membership inactivity is based on the last qualifying completed paid order; the preview's `Последний визит` follows M16.2 and exposes the latest qualifying order or active session activity, while unknown activity never qualifies.
